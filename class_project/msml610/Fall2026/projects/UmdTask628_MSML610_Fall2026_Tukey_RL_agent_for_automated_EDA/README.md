## What Tukey Does

- An agent gets a data table and must recover the causal graph that generated it
- It calls statistical tools on the training rows (independence tests,
  regressions, direction tests, mutual information), then emits a graph
- Training data come from random causal graphs, so every answer is scored
  exactly: structural distance to the true graph plus prediction on held-out rows
- In later milestones (not in this PR) the tool chooser and the graph decoder
  are trained with REINFORCE, starting from a copy of the prototype's scripted
  rule

## Quick Start

- Base image: the class template (`python:3.12-slim`), with no Dockerfile
  change
- Dependencies: `requirements.in` lists the direct ones; `requirements.txt` is
  generated by pip-compile and pinned to the versions every stored result was
  produced with (why: the packages depend on each other, see the file's header)
- The code imports the prototype
  `research/agentic_data_science/RL_for_auto_EDA_prototype.py` and the
  `helpers` package from this repository; the scripts mount the repository at
  `/git_root`
- From the repository root, initialize the `helpers` submodule once, then work
  from the project folder (every script expects it):

  ```bash
  > git submodule update --init helpers_root
  > cd class_project/msml610/Fall2026/projects/UmdTask628_MSML610_Fall2026_Tukey_RL_agent_for_automated_EDA
  > ./docker_build.sh
  > ./run_tests.sh          # the unit tests, in the container
  > ./docker_jupyter.sh     # then open tukey.API.ipynb and tukey.example.ipynb
  ```

- Run both notebooks in the container, from the host (needs `pytest` there):
  `pytest test/test_docker_tukey.py`
- Regenerate a stored result in the container, e.g. the sortability report:

  ```bash
  > ./docker_cmd.sh "cd /git_root/$(git rev-parse --show-prefix) && python tukey_results.py sortability --out results/m1/sortability.json"
  ```

  Every file's command is in the docstring of `tukey_results.py`; the
  Milestone 2 table takes about one CPU-hour

## Preliminary Results

- From local runs of later milestones, not from this PR; each result file
  arrives with its milestone's PR, see [`docs/07-progress.md`](docs/07-progress.md)
- On 600 sealed synthetic graphs (5 seeds) the trained policy beats the scripted
  rule: score -0.275 vs -0.413 (+0.138, 95% CI [0.125, 0.151]); structural
  distance 4.25 vs 5.86
- On the same graphs GES (-0.211) and DirectLiNGAM (-0.184) beat the policy;
  PC is about level
- On real protein data (Sachs et al. 2005) every method scores low: skeleton F1
  0.53 for the policy, 0.52 for GES, DirectLiNGAM and the rule, 0.58 for PC

## Open Questions

- Does learned test selection help, or only the trained decoder? The policy
  rarely calls the direction test (0.0007 calls per graph)
- Why do GES and DirectLiNGAM stay ahead?
- Messy data (missing values, drift, mixed types; spec Question 2): tested on
  synthetic corruptions only (arrives with a later PR); real messy data untested
- Human-level discovery without heuristics (spec Question 3): not shown
- Scoring Gaussian data against its equivalence class and hidden confounders
  against a PAG need the reviewers' agreement
  ([`D1`, `D2`](docs/03-decisions.md))
