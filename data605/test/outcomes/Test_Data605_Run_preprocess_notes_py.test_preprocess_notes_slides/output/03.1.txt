#### Application Deployment
- For (almost all) Internet companies, **\textcolor{red}{the application is the business}**
  - If the application breaks, the business stops
  - E.g., Amazon, Google, Facebook, online banks, travel sites, ...

- **\textcolor{darkgreen}{Problem}**
  - Release, deploy, manage, monitor applications

- **\textcolor{blue}{Solutions}**
  - Before 2000s: "bare-metal era"
  - 2000s-2010s: "virtual machine era"
  - After ~2013: "container era"

#### DevOps

:::columns
::::{.column width=65%}
- **\textcolor{red}{DevOps}** = practices combining:
  - Software development (_dev_)
  - IT operations (_ops_)

- **\textcolor{blue}{Containers revolutionized DevOps}**
  - Enable independence between app development and IT ops
    - One team creates an app
    - Another team deploys and manages apps
  - Foster collaboration and innovation
    - IT: "It doesn't work!"
    - Devs: "What? It works for me!"

#### Run on bare metal
:::columns
::::{.column width=80%}
- **\textcolor{red}{< 2000s}**
  - Running few applications per server (no virtualization)

- **\textcolor{orange}{Pros}**
  - No virtualization overhead

- **\textcolor{darkgreen}{Cons}**
  - Insecure due to no application separation
  - Expensive

- **\textcolor{teal}{Expensive / low efficiency}**
  - New server for each application
  - Hard to spec machines $\to$ buy "big and fast servers"
    - Overpowered servers at 5-10% capacity
    - Significant spending during the 2000 DotCom boom on machines and networks

- Resurfaced in 2020 with different Cloud Computing use cases

- **\textcolor{cyan}{Winners}**: Cisco, Sun Microsystems, Microsoft

#### Virtual Machine Era
:::columns
::::{.column width=75%}
- **\textcolor{red}{Circa 2000-2010: Virtual Machine}**
  - Run multiple OS copies on the same hardware

- **\textcolor{darkgreen}{Pros}**
  - Run multiple apps safely on one server
  - Use existing servers with spare capacity

- **\textcolor{blue}{Cons}**
  - Each VM needs an OS (wastes CPU, RAM, disk)
  - Buy OS license
  - Monitor and patch each OS
  - Slow boot times

- **\textcolor{violet}{Winners}**: VMWare, RedHat, Citrix

#### Containers Era
:::columns
::::{.column width=60%}
- **\textcolor{red}{Circa 2013: Docker becomes ubiquitous}**

- **\textcolor{orange}{Docker}**
  - Didn't invent containers
  - Made containers simple and mainstream

- Linux supported containers
  - Kernel namespaces
  - Control groups
  - Union filesystems

- **\textcolor{darkgreen}{Pros}**
  - Containers are fast and portable
  - Don't require a full OS
  - All run on a single host
  - Reduce OS licensing costs
  - Reduce OS patching and maintenance

#### Serverless Computing
- **\textcolor{red}{Containers run in an OS, OS runs on a host}**
  - **\textcolor{darkgreen}{Where is the host running?}**
    - Local (your laptop)
    - On-premise (your computer in a rack)
    - Cloud instance (e.g., AWS EC2)
  - **\textcolor{blue}{How is the host running?}**
    - On a bare-metal server
    - On a virtual machine
    - On a virtual machine running on a virtual machine

- **\textcolor{violet}{Serverless computing}**
  - Application runs without concern for _"how"_ or _"where"_
  - E.g., AWS Lambda

#### HW vs OS Virtualization
:::columns
::::{.column width=55%}

- **\textcolor{red}{Hypervisor performs HW virtualization}**
  - Carves physical hardware into VMs
  - Allocates CPUs, RAM, and storage to a VM
  - Like having multiple computers

- "Virtual machine tax"
  - Running 3 apps requires 3 VMs
    - Each VM takes time to start
    - Consumes CPU, RAM, and storage
    - Needs an OS license
    - Requires admins and patching
  - You just want to run 3 apps!

\vspace{1cm}
- **\textcolor{blue}{Containers perform OS virtualization}**
  - It's like having multiple isolated environments within the same OS

#### Docker: Client-Server

:::columns
::::{.column width=55%}
- Docker relies on a **\textcolor{red}{client-server architecture}**

- **\textcolor{darkgreen}{Docker client}**
  - Command line interface
  - Communicates with the server through an IPC socket
    - E.g., `/var/run/docker.sock` or IP port

- **\textcolor{blue}{Docker engine}**
  - Runs and manages containers
  - Modular, built from OCI-compliant subsystems
    - E.g., docker daemon, `containerd`, `runc`, plugins for networking and
      storage

#### Docker Architecture

:::columns
::::{.column width=60%}
- **\textcolor{red}{Docker runtime}**
  - `runc`: Start and stop containers
  - `containerd`
    - Pull images
    - Create containers, volumes, network interfaces

- **\textcolor{darkgreen}{Docker engine}**
  - `dockerd`
    - Expose remote API
    - Manage images, volumes, networks

- **\textcolor{blue}{Docker orchestration}**
  - `docker swarm`
    - Manage clusters of nodes
    - Often replaced by Kubernetes

- **\textcolor{violet}{Open Container Initiative (OCI)}**
  - Standardize low-level components of container infrastructure
  - E.g., image format, runtime API
  - Evolution of Docker standards

#### Docker Container

- **\textcolor{red}{Docker Container}**
  - Unit of computation
  - Lightweight, stand-alone, executable software package

- **\textcolor{darkgreen}{Includes everything needed to run}**
  - Code
  - Runtime/system libraries
  - Settings

- **\textcolor{blue}{Run-time object}**
  - Docker images are build-time objects
  - Like program running (container) vs program code (image)

#### Docker Image
- **\textcolor{red}{Docker Image}**
  - Unit of deployment

- **\textcolor{blue}{Contains everything needed to run an app}**
  - Application code
  - Application dependencies
  - Minimal OS support
  - File system

- Users can
  - Build images from Dockerfiles
  - Pull pre-built images from a registry

- Multiple layers stacked
  - Typically a few 100s of MBs

#### Docker Image Layers
:::columns
::::{.column width=60%}
- **\textcolor{red}{Docker image}** is a configuration file listing layers and metadata
  - Composed of read-only layers
  - Each layer is independent
  - Each layer comprises many files

- **\textcolor{darkgreen}{Docker driver}**
  - Stacks layers as a unified filesystem
  - Implements copy-on-write behavior
  - Files from top layers can obscure files from bottom layers

- **\textcolor{blue}{Layer hash}**
  - Each layer has a hash based on content
  - Layers are pulled and pushed in a compressed format

- **\textcolor{violet}{Image hash}**
  - Each image has a hash
  - Hash is a function of the config file and layers
  - Image changes generate a new hash

#### Docker: Container Data
- A container has access to different data

- **\textcolor{red}{Container storage}**
  - Copy-on-write layer in the image
  - Ephemeral (temporary data)
  - Data persists until the container is removed
    - Stopping or pausing a container doesn't lose data
  - Containers are immutable
    - Avoid writing persistent data into containers

- **\textcolor{darkgreen}{Bind-mount a local dir}**
  - Mount a local directory to a directory inside a container

- **\textcolor{blue}{Docker volumes}**
  - Volumes exist separately from the container
    - E.g., store PostgreSQL DB content
  - State is permanent across container invocations
  - Shareable across containers

#### Docker Repos
:::columns
::::{.column width=55%}
- **\textcolor{red}{Docker Repo (Registry)}**
  - E.g., DockerHub, AWS ECR
  - Store Docker images
    - `<registry>/<repo>:<tag>`
    - E.g., `docker.io/alpine:latest`
  - Some repos are vetted by Docker
  - Unofficial repos shouldn't be trusted
  - E.g., https://hub.docker.com/

#### Devops = Devs + Ops

- Containerize app
  - Create Dockerfile
  - Instructions to build image
- Build image
- Run app as container
- Test locally
::::

- **\textcolor{blue}{Ops}**
- Download container images
  - Filesystem, application, dependencies
- Start / destroy containers
- Reproduce issues easily
  - "Here is the log"
  - Run command line
  - Deploy on test system and debug
