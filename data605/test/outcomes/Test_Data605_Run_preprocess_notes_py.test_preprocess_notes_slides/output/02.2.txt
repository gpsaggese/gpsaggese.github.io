#### Git Branching
::: columns
:::: {.column width=55%}
- **\textcolor{red}{Branching}**
  - Diverge from the main development line
- **\textcolor{darkgreen}{Why branch?}**
  - Work without affecting the main code
  - Avoid changes in the main branch
  - Merge code downstream for updates
  - Merge code upstream after completion

::::
:::: {.column width=40%}

![](data605/lectures_source/images/lecture_2/lec_2_slide_15_image_1.png)

::::
:::

- **\textcolor{blue}{Git branching is lightweight}**
  - Instantaneous
  - A branch is a pointer to a commit
  - Git stores data as snapshots, not file differences

- **\textcolor{violet}{Git workflows branch and merge often}**
  - Multiple times a day
  - Surprising for users of centralized VCS
    - E.g., branch before lunch
  - Branches are cheap
    - Use them to isolate and organize work

#### Git Branching
::: columns
:::: {.column width=55%}
- \textcolor{blue}{\texttt{master}} (or \textcolor{blue}{\texttt{main}}) is a normal branch
  - Pointer to the last commit
  - Moves forward with each commit

- \textcolor{blue}{\texttt{HEAD}}
  - Pointer to the current branch
  - E.g., \textcolor{blue}{\texttt{master}}, \textcolor{blue}{\texttt{testing}}
  - \textcolor{blue}{\texttt{git checkout <BRANCH>}} moves across branches

- \textcolor{blue}{\texttt{git branch testing}}
  - Creates a new pointer \textcolor{blue}{\texttt{testing}}
  - Points to the current commit
  - Pointer is movable

- Divergent history
  - Work progresses in two "split" branches

#### Git Checkout
::: columns
:::: {.column width=55%}
- \textcolor{blue}{\texttt{git checkout}} switches branches
  - Moves \textcolor{blue}{\texttt{HEAD}} pointer to the new branch
  - Changes files in the working directory to match the branch pointer
- E.g., two branches, \textcolor{blue}{\texttt{master}} and \textcolor{blue}{\texttt{testing}}
  - You are on \textcolor{blue}{\texttt{master}}
  - \textcolor{blue}{\texttt{git checkout testing}}
  - Pointer moves, working directory changes
  - Keep working and commit on \textcolor{blue}{\texttt{testing}}
  - Pointer to \textcolor{blue}{\texttt{testing}} moves forward

#### Fast Forward Merge
  - Merge a commit \textcolor{blue}{\texttt{Y}} with a commit \textcolor{blue}{\texttt{X}} that can be reached by following the
    history of commit \textcolor{blue}{\texttt{Y}}

- There is no divergent history to merge
  - Git simply moves the branch pointer forward from X to Y

::: columns
:::: {.column width=55%}
- **\textcolor{red}{Mental model}**: a branch is just a pointer that indicates where the tip of
  the branch is
- E.g., \textcolor{blue}{\texttt{C4'}} is reachable from \textcolor{blue}{\texttt{C3}}
  \begingroup \small \color{blue}
  ```
  > git checkout master
  > git merge experiment
  ```
  \endgroup
- Git moves the pointer of master to \textcolor{blue}{\texttt{C4'}}

#### Merging Conflicts
::: columns
:::: {.column width=55%}
- Tutorial:
  - [Merging conflicts](https://github.com/gpsaggese/gpsaggese.github.io/blob/master/data605/tutorials/tutorial_git/tutorial_git.md#merging-conflicts)

- Sometimes **\textcolor{red}{Git can't merge}**, e.g.,
  - The same file has been modified by both branches
  - One file was modified by one branch and deleted by another

- **\textcolor{darkgreen}{Git}**:
  - Does not create a merge commit
  - Pauses to let you resolve the conflict
  - Adds conflict resolution markers

- **\textcolor{blue}{User merges manually}**
  - Edit the files using \textcolor{blue}{\texttt{git mergetool}}
  - Use \textcolor{blue}{\texttt{git add}} to mark as resolved
  - Use \textcolor{blue}{\texttt{git commit}} to finalize the merge
  - Use PyCharm or VS Code for assistance

#### Git Rebasing

- In Git, there are **\textcolor{red}{two ways of merging divergent history}**
- E.g., consider \textcolor{blue}{\texttt{master}} and \textcolor{blue}{\texttt{experiment}} have a common ancestor \textcolor{blue}{\texttt{C2}}

::: columns
:::: {.column width=60%}

- **\textcolor{darkgreen}{Merge}**
  - Go to the target branch
    \begingroup \small \color{blue}
    ```
    > git checkout master
    > git merge experiment
    ```
    \endgroup
  - Create a new snapshot \textcolor{blue}{\texttt{C5}} and commit

- **\textcolor{blue}{Rebase}**
  - Go to the branch to rebase
    \begingroup \small \color{blue}
    ```
    > git checkout experiment
    > git rebase master
    ```
    \endgroup
  - Rebase algorithm:
    - Get all the changes committed in the branch (\textcolor{blue}{\texttt{C4}}) where we are on
      (\textcolor{blue}{\texttt{experiment}}) since the common ancestor (\textcolor{blue}{\texttt{C2}})
    - Sync to the branch that we are rebasing onto (\textcolor{blue}{\texttt{master}} at \textcolor{blue}{\texttt{C3}})
    - Apply the changes \textcolor{blue}{\texttt{C4}}
    - Only the current branch is affected
    - Finally, fast forward \textcolor{blue}{\texttt{experiment}}
::::
:::: {.column width=40%}

#### Uses of Rebase
::: columns
:::: {.column width=55%}
- **\textcolor{red}{Rebasing makes for a cleaner history}**
  - The history looks like all the work happened in series
  - Although in reality, it happened in parallel to the development in the
    master branch
- **\textcolor{blue}{Rebasing to contribute to a project}**
  - Developer
    - You are contributing to a project that you don't maintain
    - You work on your branch
    - When you are ready to integrate your work, rebase your work onto
      \textcolor{blue}{\texttt{origin/master}}
  - The maintainer
    - Does not have to do any integration work
    - Does just a fast forward or a clean apply (no conflicts)

#### Golden Rule of Rebasing
- **\textcolor{red}{Remember}**: rebasing means abandoning existing commits and creating new ones
  that are similar but different

::: columns
:::: {.column width=55%}

- **\textcolor{darkgreen}{Problem}**
  - You push commits to a remote
  - Others pull commits and base work on them
  - You rewrite commits with \textcolor{blue}{\texttt{git rebase}}
  - You push again with \textcolor{blue}{\texttt{git push --force}}
  - Collaborators must re-merge work

- **\textcolor{blue}{Solution}**
  - Strict: _"Do not ever rebase commits outside your repository"_
  - Loose: _"Rebase your branch if only you use it, even if pushed to a server"_

#### Rebase vs Merge: Philosophical Considerations
- **\textcolor{red}{Many man-centuries have been wasted}** discussing rebase-vs-merge at the
  watercooler
  - Total waste of time! Tell people to get back to work!

- When you contribute to a project often people decide for you based on their
  preference

- **\textcolor{darkgreen}{Best of the merge-vs-rebase approaches}**
  - Rebase changes you've made in your local repo
    - Even if you have pushed but you know the branch is yours
    - Use \textcolor{blue}{\texttt{git pull --rebase}} to clean up the history of your work
    - If the branch is shared with others then you need to definitively `git
      merge`
  - Only \textcolor{blue}{\texttt{git merge}} to master to preserve the history of how something was built

- **\textcolor{blue}{Personally}**
  - I like to squash-and-merge branches to \textcolor{blue}{\texttt{master}}
  - Rarely are my commits "complete"; they are just checkpoints

#### Remote Branches
- **\textcolor{red}{Remote branches}** are pointers to branches in remote repositories
  \begingroup \small \color{blue}
  ```
  > git remote -v
  origin  git@github.com:gpsaggese/umd_classes.git (fetch)
  origin  git@github.com:gpsaggese/umd_classes.git (push)
  ```
  \endgroup

- **\textcolor{blue}{Tracking branches}**
  - Local references representing the state of the remote repository
  - E.g., \textcolor{blue}{\texttt{master}} tracks \textcolor{blue}{\texttt{origin/master}}
  - You can't change the remote branch (e.g., \textcolor{blue}{\texttt{origin/master}})
  - You can change the tracking branch (e.g., \textcolor{blue}{\texttt{master}})
  - Git updates tracking branches when you do \textcolor{blue}{\texttt{git fetch origin}} (or \textcolor{blue}{\texttt{git pull}})

- To share code in a local branch you need to push it to a remote
  \begingroup \small \color{blue}
  ```
  > git push origin serverfix
  ```
  \endgroup

- To work on it
  \begingroup \small \color{blue}
  ```
  > git checkout -b serverfix origin/serverfix
  ```
  \endgroup

#### Centralized Workflow
::: columns
:::: {.column width=55%}
- **\textcolor{red}{Centralized workflow in centralized VCS}**
  - Developers:
    - Check out the code from the central repo on their computer
    - Modify the code locally
    - Push it back to the central hub (assuming no conflicts with the latest
      copy, otherwise they need to merge)

- **\textcolor{blue}{Centralized workflow in Git}**
  - Developers:
    - Have push (i.e., write) access to the central repo
    - Need to fetch and then merge
    - Cannot push code that will overwrite each other's code (only fast-forward
      changes)

#### Forking Workflows
- Typically, developers don't have permissions to update branches directly on a
  project
  - Read-write permissions for core contributors
  - Read-only for everybody else

- **\textcolor{red}{Solution}**
  - "Forking" a repo
  - External contributors:
    - Clone the repo and create a branch with their work
    - Create a writable fork of the project
    - Push branches to the fork
    - Prepare a PR (Pull Request) with their work
  - Project maintainer:
    - Reviews PRs
    - Accepts PRs
    - Integrates PRs
  - In practice, it's the project maintainer who pulls the code when it's ready,
    instead of external contributors pushing the code

::: columns
:::: {.column width=80%}
- **\textcolor{blue}{Aka "GitHub workflow"}**
  - The "innovation" was forking (Fork me on GitHub!)
  - GitHub was acquired by Microsoft for 7.5 billion USD

#### Integration-Manager Workflow
::: columns
:::: {.column width=55%}
- This is the classical model for open-source development
  - E.g., Linux, GitHub (forking) workflow
::::
:::: {.column width=40%}

![](data605/lectures_source/images/lecture_2/lec_2_slide_31_image_1.png)

::::
:::

1. **\textcolor{red}{One repo is the official project}**
   - Only the project maintainer pushes to the public repo
   - E.g., \textcolor{blue}{\texttt{causify-ai/csfy}}

2. **\textcolor{darkgreen}{Each contributor}**
   - Has read access to everyone else's public repo
   - Forks the project into a private copy
     - Write access to their own public repo
     - E.g., \textcolor{blue}{\texttt{gpsaggese/csfy}}
   - Makes changes
   - Pushes changes to their own public copy
   - Sends a pull request to the maintainer asking to merge changes

3. **\textcolor{blue}{The maintainer}**
   - Adds the contributor's repo as a remote
   - Merges the changes into a local branch
   - Tests changes locally
   - Pushes the branch to the official repo

#### Dot notation

#### Advanced Git

- **\textcolor{red}{Stashing}**
  - Copy the state of your working directory (e.g., modified and staged files)
  - Save it in a stack
  - Apply it later

- **\textcolor{darkgreen}{Cherry-picking}**
  - Apply a single commit from one branch onto another

- **\textcolor{blue}{rerere}**
  - = "Reuse Recorded Resolution"
  - Git caches how to solve certain conflicts
- **\textcolor{violet}{Submodules / subtrees}**
  - Projects including other Git projects

#### Advanced Git
- **\textcolor{red}{bisect}**
  - \textcolor{blue}{\texttt{git bisect}} helps identify the commit that introduced a bug
    - Bug appears at the top of the tree
    - Unknown revision where it started
    - Script returns 0 if good, non-zero if bad
    - \textcolor{blue}{\texttt{git bisect}} finds the revision where the script changes from good to bad

- **\textcolor{darkgreen}{filter-branch}**
  - Rewrite repository history in a scriptable way
    - E.g., change email, remove sensitive file
  - Check out each version, run a command, commit the result

- **\textcolor{blue}{Hooks}**
  - Run scripts before committing, merging, etc
