# GitHub Project Automation Product Requirements

- Generated by `.claude/skills/project.write_prd/SKILL.md`

## Goal

- Make GitHub apply and enforce the rules for issues, PRs, and GitHub Projects, so
  that people and agents follow them without having to remember them
- Background:
  - Issue [#803](https://github.com/gpsaggese/gpsaggese.github.io/issues/803)

    [`idea.md`](/dev_scripts_umd_classes/project_automation/idea.md)
  - Answers to the questions of #803:

## Users and Use Cases

- GP (owner and reviewer): see in one place the issues that wait for his review, and
  stop fixing issues and PRs by hand
- Contributors (students, RAs, interns): find one rule for each convention, and learn
  that they broke a rule when they open the issue or the PR, not at review time
- AI agents: create issues and PRs that follow the same rules as humans, and get the
  same checks
- Project leads: start a new project that already has the conventions

## Requirements: Rules

### `R1` (One rule per convention)

- Each convention (statuses, closing keywords, checkbox vs sub-issue vs issue, title
  prefix, one project per issue) is stated in exactly one doc, and every other doc
  that mentions it links to that doc

### `R2` (No obsolete references)

- The work-organization docs contain no link or instruction that does not work for
  the projects of the user `gpsaggese`, e.g., the `cryptokaizen` org, the `cmamp`
  repo, or organization project templates

## Requirements: PRs

### `R3` (PR linked to an issue)

- A PR that refers to no issue fails a check, with a message that says how to link
  it

### `R4` (Close only from the last PR)

- Merging the PR that finishes an issue closes the issue, and merging a PR that is
  one step of the issue leaves it open

### `R5` (Standard PR description)

- A new PR starts with a description that has fixed sections and a size limit per
  section
- A description over its limit gets a warning on the PR

### `R6` (No open comments or boxes at merge)

- A PR with an unresolved review conversation or an unchecked box in its
  description cannot be merged

### `R7` (Submodule on master)

- A PR that points a submodule to a commit that is not on the `master` branch of the
  submodule cannot be merged

## Requirements: Issues

### `R8` (Project prefix in the title)

- An issue whose title does not start with the short name of a project, e.g.,
  `Noesis:`, is flagged when it is opened or edited

### `R9` (One project per issue)

- An issue that is in no project or in more than one project is flagged

### `R10` (Close only when the boxes are done)

- An issue closed as completed with an unchecked box is reopened with a comment that
  lists the open boxes
- A box that points to another issue or gives a reason for not doing it does not
  count as open

## Requirements: Boards

### `R11` (Review status)

- Every project has an `In review` status, and one view lists the issues in it

### `R12` (Card follows its PR)

- The card of an issue moves with the events of its PRs, without a person moving it:
  - To `In progress` when a draft PR for the issue is opened
  - To `In review` when the PR is ready for review or GP is asked to review it
  - Back to `In progress` when a reviewer requests changes
  - To `Done` when the issue is closed

### `R13` (No stray auto-add)

- A closed project does not add new issues to itself

## Requirements: Project Template

### `R14` (Template with the conventions)

- Copying the `Template` project gives a project with the agreed statuses, fields,
  views, and workflows

### `R15` (Existing projects in sync)

- A command lists the projects that differ from `Template` and applies the missing
  statuses, fields, and views to them

## Non-Goals

- Moving the projects from the user `gpsaggese` to an organization
- Changing how non-technical work is tracked in Asana
- Reviewing or merging PRs automatically: a human merges every PR
- Editing the content of an issue or a PR beyond adding a comment, a label, or
  reopening an issue
- Migrating the closed issues to the new conventions

## Success Metrics

- Linked PRs: 100% of the PRs merged into `master` in a month refer to an issue,
  counted from the merged PRs
- Prefixed issues: 0 open issues without a project prefix, counted with a search on
  the open issues
- Review queue: GP finds the issues waiting for him in one view, instead of
  scanning every project
- Submodule breaks: 0 merged PRs that point a submodule outside `master`, counted
  from the failed checks and the incidents like #874

## Constraints and Assumptions

- The projects are owned by the user `gpsaggese`:
  `github.com/users/gpsaggese/projects`
- The repo is public, and contributors open PRs from branches and from forks
- `GITHUB_TOKEN` cannot access projects, so the board automation needs a token with
  the `project` scope, created by the owner
- The settings (branch protection, project workflows, secrets) can be changed only by
  the owner of the repo and of the projects
- AI agents create many of the issues and PRs, so every rule must be stated in
  markdown in the repo
